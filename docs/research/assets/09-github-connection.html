How the GitHub connection works

Agents read a company's GitHub repositories: the SQL, dbt models and enums that explain their data, and the commits and pull requests that explain why a number moved. Read-only first; pull requests later, behind approval.

The whole picture

T-J1 · T-J2 · T-J3 · T-J4 · T-J5

Three parties. The customer's GitHub, where they install our App and choose repositories. Argentum, which keeps a text copy of those repositories and gives bound agents tools to search it. And the people who connect it and ask the questions.

  1. An admin presses Connect GitHub. T-J1
  2. GitHub installs the App on the repositories the admin picks. Argentum proves the installation belongs to that admin before saving it. T-J1
  3. GitHub sends signed webhooks: a push, or the App being removed. T-J1 · T-J2
  4. A push queues one sync for that repository. Several pushes in a row become one sync. T-J2
  5. The worker asks for a token that lasts at most an hour and covers only the repositories it needs. Tokens are never saved. T-J1
  6. One download per sync (the repository archive). Commits, PRs and issues are read live and cached with ETags. T-J2 · T-J5
  7. Text files go into Postgres. Agent tools search and read line ranges from that copy, not from GitHub. T-J2 · T-J4
  8. Someone asks a question of an agent bound to the repository. Every other agent works exactly as it does today. T-J3
  9. The website widget never gets repository tools. The person there is the company's own customer. T-J3

1 · Connecting a GitHub account

T-J1 · about 3 days

This happens once per company. The admin never pastes a token. GitHub's install page is where they choose which repositories Argentum may see, and they can change that later on GitHub.

Why a GitHub App, not a personal tokenA personal token belongs to one employee and stops working when they leave. It also sees everything they can see. An App sees only what the company picks.
Why step 10 existsThe installation_id in the redirect URL can be edited by anyone. Without that check, one company could attach another company's code. This is the most important test in the track.
What is keptWhich installation, which account, which repositories. No token of any kind.

2 · Keeping a copy up to date

T-J2 · about 3.5 days

Argentum keeps a text copy of each enabled repository's default branch. A push makes it update within moments. A background check every hour catches any push GitHub failed to announce.

Why a copy, instead of asking GitHub each timeGitHub's code search has no regex and allows 10 searches a minute. Reading file by file hits its other limits fast. One archive download per push avoids both.
Why the hourly checkGitHub never retries a webhook it failed to deliver. Asking “has the branch moved?” with an ETag costs nothing when the answer is no.
Why no git cloneArgentum runs no external programs, and the worker has 512 MB of memory. The archive is read as a stream, so memory stays flat whatever the repository's size.

3 · Answering a question from the repository

T-J3 · T-J4 · T-J5 · T-J6

The agent searches first, then reads only the lines the search found, and answers with a link to those exact lines at the commit it read. Returning line ranges instead of whole files is what keeps the cost down.

The guardrail change (step 4)Today the topic check refuses questions about code. For an agent bound to a repository it asks the same question it always has, “whose data answers this?”, and the company's own code counts. Needs your confirmation.
Text written by outsidersAn issue comment from someone outside the company is treated like an uploaded PDF. If the agent has read one, any action it proposes needs approval.
Every answer is datedResults carry the commit and when it was copied, so “as of commit abc1234, synced 14:02” can be stated rather than assumed.

4 · Later: opening a pull request

T-J10 · T-J11 · not scheduled

This uses a second App with write access, installed only by companies that want it, on the repositories they choose. The agent proposes a change and a person approves it after reading the exact diff. Nothing reaches GitHub before that approval.

Why a second AppAdding write access to the first App would make every connected company approve a new permission. Companies that only want reading would never see that request.
Why step 2It blocks a known attack. A public issue tells an agent to copy private code into a public PR, and approval alone relies on the reviewer spotting it.
What it does not doIt does not run tests. The repository's own CI does, and the agent reads the result back. Changes that need a build loop go to a coding agent the company already runs (spike T-J12).

What is stored, and what never is

decisions 2, 3, 6, 9, 10

Stored in Argentum

  • Which GitHub installation belongs to which company
  • The repositories enabled, and each one's include/exclude paths
  • A text copy of each enabled default branch, in 200-line chunks under a search index, within limits: 512 KB per file, 50 MB per repository, 200 MB per company
  • Which agents may read which repositories. Empty means none
  • When it last synced, and why a sync failed

Never stored, never offered

  • Any GitHub access token. They are minted when needed and expire within an hour
  • The admin's own GitHub login token. It is used once to prove ownership, then discarded
  • Binaries, images, vendored code, lockfiles
  • Other branches. A file at another branch or commit is read live, one file at a time
  • Repository tools on the website widget

Deleting a company's data removes its copies. Disabling a repository deletes its files. Removing the App on GitHub disables everything it granted, either on the webhook or at the next hourly check.

What one repository question costs

research §5 · measured by T-J7

GitHub charges nothing here. The cost is model tokens. Production's model is re-sent everything in the conversation at every step, with no caching, so what matters is how much each tool returns and how many steps the agent needs.

ApproachA typical 4-step questionWhy
This design: search, then read line ranges≈ $0.066 Three small tools. About 1,500 tokens for a search and 3,000 for each range read.
Same tools, reading whole files≈ $0.10 Two 60 KB files stay in the context for every later step.
GitHub's own MCP server≈ $0.12+ Every tool's definition is re-sent at every step (illustrated at 15,000 tokens). Files over 256 KB fail outright.
An agent with no repository bound$0 extra The tools, their instructions and the repository summary are simply not there.

Estimates, not measurements: arithmetic on the real price of moonshotai/kimi-k2.6 ($0.95 per million input tokens, $4.00 per million output tokens). T-J7 replaces them with numbers read from usage_events.

Words on this page

GitHub App
An integration registered once by Smartsoft. Each company installs it on its own GitHub account and chooses repositories.
Installation
One company's install of the App. Argentum saves its id, once ownership has been proven.
Installation token
A key GitHub issues on request. It lasts up to an hour and can be limited to specific repositories and read-only access.
Webhook
GitHub calling Argentum when something happens, such as a push. Signed, so a forged call is rejected.
ETag
A fingerprint of a response. Asking “has this changed since this ETag?” returns a free 304 when it hasn't.
Bound agent
An agent an admin has allowed to read a repository. Only bound agents get repository tools.
Reconciler
The hourly check that catches any push whose webhook never arrived.
